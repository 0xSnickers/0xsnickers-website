# x402 打赏页面实现方案

## 目标

在当前站点新增一个独立的 `/donate` 打赏页面，让用户可以用 **USDC on Base** 支持站点内容，并在支付成功后看到明确反馈。

第一版目标是跑通一条最短、可验证、可上线的链路：

- 有独立打赏页。
- 只支持固定金额：`1 / 5 / 10 USDC`。
- 使用 x402 SDK 完成 `402 Payment Required` 握手和服务端结算。
- 服务端写入 Supabase `donations` 表。
- 支付成功后展示金额、时间、可选交易信息。

第一版暂不做：

- 自定义金额。
- 支持者排行榜。
- 多链支持。
- 会员解锁。
- 首页结构大改。

自定义金额会让服务端动态 payment requirements 复杂很多，建议放到 Phase 2。

---

## 当前项目约束

当前项目是：

- Next.js App Router。
- 首页和文档体系已存在。
- 已使用 Supabase，但当前 `src/lib/supabase/client.ts` 使用的是 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`。
- 打赏记录属于服务端可信写入路径，不能使用前端 publishable key 直接写。

因此第一版要新增：

- `/donate` 页面。
- `POST /api/donations` 支付入口。
- 服务端 Supabase client。
- x402 配置与固定金额表。
- Supabase migration SQL。

## x402 接入原则

x402 最适合的模型是：

1. 客户端请求一个需要付费的 API。
2. 服务端返回 `402 Payment Required` 和 payment requirements。
3. 客户端完成钱包签名/支付授权后重试请求。
4. 服务端通过 facilitator 校验并结算。
5. 业务 handler 执行真实动作。

对于打赏页面，付费动作就是：

```text
POST /api/donations
```

第一版建议使用当前 x402 SDK：

```bash
npm install @x402/next @x402/evm @x402/core @x402/fetch viem
```

服务端优先使用 `@x402/next` 的 Route Handler wrapper。第一版需要 `onProtectedRequest` 和 `onAfterSettle` 钩子，所以使用 `withX402FromHTTPServer` + `x402HTTPResourceServer`。不要手写 `PAYMENT-SIGNATURE`、`PAYMENT-REQUIRED` 或历史版本里的 `X-Payment` 细节，header 协议以 SDK 为准。

## 网络与 facilitator 策略

### Phase 1：测试网优先

优先跑通：

- Network：Base Sepolia
- Asset：USDC on Base Sepolia
- Facilitator：x402 官方测试 facilitator

这样不用一开始处理真实资金和 CDP 生产密钥。

### Phase 1.5：主网小额

测试网成功后再切：

- Network：Base mainnet
- Asset：USDC on Base
- Facilitator：CDP production facilitator
- 金额仍固定为 `1 / 5 / 10 USDC`

主网环境变量需要使用当前 CDP/x402 文档推荐命名：

```env
CDP_API_KEY_ID=
CDP_API_KEY_SECRET=
```

不要使用过期或不明确的 `COINBASE_API_KEY / COINBASE_API_SECRET`。

## 页面设计

### `/donate`

页面文案保持轻量：

- 标题：`支持我继续写笔记`
- 副文案：`如果这些内容对你有帮助，可以用 USDC on Base 支持一下。`
- 固定档位：`1 USDC / 5 USDC / 10 USDC`
- 按钮：`打赏 1 USDC`
- 成功提示：`打赏成功，感谢支持。`

页面状态至少包含：

- 默认态。
- 金额选中态。
- 支付中。
- 成功。
- 失败。

## API 设计

### `POST /api/donations?tier=coffee&requestId=uuid`

第一版使用 query string 传参：

```text
POST /api/donations?tier=coffee&requestId=8f6d8e5e-6a2f-4d63-8c72-9b7b3c8a2f30
```

服务端只信任 `tier`，不信任前端金额。

这里不使用 JSON body，是为了避免 x402 的 Next adapter 在生成动态 payment requirements 时读取 body 并消费 request stream。`tier` 和 `requestId` 只作为路由级参数，服务端仍会重新校验。

固定档位建议：

```ts
const DONATION_TIERS = {
  coffee: { amount: '1.00', label: 'Coffee' },
  note: { amount: '5.00', label: 'Good note' },
  builder: { amount: '10.00', label: 'Builder fuel' },
} as const;
```

服务端根据 `tier` 生成或匹配 x402 payment requirements。

### 成功响应

```json
{
  "success": true,
  "donation": {
    "id": "uuid",
    "requestId": "uuid",
    "tier": "coffee",
    "amount": "1.00",
    "currency": "USDC",
    "chain": "eip155:84532",
    "txHash": "0x...",
    "payerAddress": "0x...",
    "receiverAddress": "0x...",
    "createdAt": "2026-07-03T12:34:56.000Z"
  }
}
```

## Supabase 表设计

新增表：`donations`

建议 SQL：

```sql
create table if not exists public.donations (
  id uuid primary key default gen_random_uuid(),
  request_id uuid not null unique,
  tier text not null,
  amount numeric(18, 6) not null,
  currency text not null default 'USDC',
  chain text not null,
  tx_hash text,
  payer_address text,
  receiver_address text not null,
  facilitator_response jsonb,
  status text not null default 'pending',
  verified_at timestamptz,
  created_at timestamptz not null default now(),
  constraint donations_amount_positive check (amount > 0),
  constraint donations_status_check check (status in ('pending', 'confirmed', 'failed'))
);

alter table public.donations enable row level security;
```

第一版不需要公开支持者列表，因此可以不创建 anon select policy。服务端使用 service role 写入。

如果后续要展示支持者列表，再新增只读 policy，并确认 Supabase Data API grants/RLS 一起配置。

第一版只允许服务端写入，migration 里显式给 `service_role` 授权：

```sql
grant select, insert, update on table public.donations to service_role;
```

## 环境变量

新增：

```env
X402_RECEIVER_ADDRESS=
X402_NETWORK=eip155:84532
NEXT_PUBLIC_X402_NETWORK=eip155:84532
X402_FACILITATOR_URL=https://facilitator.x402.org
CDP_API_KEY_ID=
CDP_API_KEY_SECRET=
SUPABASE_SERVICE_ROLE_KEY=
```

已有：

```env
NEXT_PUBLIC_SUPABASE_URL=
NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=
```

安全要求：

- `SUPABASE_SERVICE_ROLE_KEY` 只能服务端使用。
- `CDP_API_KEY_SECRET` 只能服务端使用。
- 不要加 `NEXT_PUBLIC_` 前缀。
- `NEXT_PUBLIC_X402_NETWORK` 不是密钥，用于让前端钱包链和服务端 `X402_NETWORK` 保持一致。

## 幂等与安全

第一版必须做：

- `requestId` 必填，前端生成 UUID。
- `request_id` 数据库唯一约束，避免重复点击重复写入。
- 同一个 `requestId` 如果已经 `confirmed`，允许幂等返回已有记录。
- 同一个 `requestId` 如果仍是 `pending`，拒绝重复支付流程，避免并发重复结算。
- 结算失败或业务 handler 取消结算时，把记录标为 `failed`，避免永久卡在 `pending`。
- 服务端只接受固定 `tier`。
- 服务端重新计算金额，不使用前端 amount。
- `receiver_address` 必须等于环境变量配置。
- 如果 SDK 能返回 payer/tx/facilitator payload，尽量落库，便于排查。

## 分阶段实施

### Phase 1：固定金额 + 测试网

- `/donate` 页面。
- `1 / 5 / 10 USDC` 固定档位。
- `POST /api/donations`。
- `withX402FromHTTPServer` 包裹 Route Handler。
- Supabase service role 写库。
- 成功/失败 UI。

### Phase 2：体验增强

- 自定义金额。
- 昵称/留言。
- 更完整的交易哈希展示。
- 主网小额测试。

### Phase 3：展示能力

- 最近打赏记录。
- 支持者列表。
- 累计金额。

---

## 第一版验收标准

- `/donate` 页面可打开。
- 用户可选择固定档位。
- 未支付请求返回 x402 的 `402` 响应。
- 支付后重试请求成功。
- 成功记录写入 Supabase。
- 重复 `requestId` 不会重复写入。
- 页面能展示成功或失败。
- 构建通过。
- 敏感密钥没有进入客户端 bundle。
